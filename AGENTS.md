# Project instructions

These instructions govern the entire repository and all descendants.

## Active scope: Progree dual-track internship

The repository supports two separate workstreams: **Python Programming** and
**Digital Marketing & Branding**. Preserve the approved Python baseline while
the Digital Marketing workstream is planned, researched, reviewed, and reported
independently. The relevant source briefs are:

- `Python Programming Tasks & Instructions.pdf` for Python;
- `Digital Marketing & Branding Tasks & Instructions.md` for the available
  transcription of the Digital Marketing brief; and
- `Text Message 1.md` and `Text Message 2.md` for shared submission notices.

Tasks 2–4 are the intended deliverables in each track. Task 1 is optional and
deferred unless separately authorized. Digital Marketing is active scope, not
context-only material.

## Workstream separation

- Keep the existing Python sources in their current paths for compatibility.
  Do not replace approved implementation, tests, evidence, or the historical
  Python report without a separately reviewed change.
- Use `python/` for Python-track planning, evidence pointers, and future
  deliverable guidance; use `digital_marketing/` for Marketing planning,
  research records, evidence, and future deliverables.
- Produce one report per track. Generate a combined portfolio only after the
  submission form's multi-track behavior is verified.

## Evidence and research integrity

- Python claims must come from executable source, tests, and captured runs.
- Marketing observations must name a public source URL and collection date.
  Mark inaccessible metrics unavailable. Distinguish observable facts,
  estimates, assumptions, proposed targets, and model outputs.
- Never invent followers, post counts, engagement, search volumes, rankings,
  campaign performance, analytics access, or first-party business data.
- Do not publish social posts, launch advertising, edit live websites, send
  email, buy media, or submit forms without explicit authorization.

## Privacy and external actions

This repository is public. Never commit an offer letter or participant identity,
student identifier, contact details, signatures, private images, credentials,
or personal files. Keep optional private submission assets in ignored local
locations and use identity-neutral public report templates. Do not infer that a
Digital Marketing offer letter authorizes the Python track.

## Review gates and engineering practice

- Work in reviewable phases. Complete and verify the authorized phase, then
  wait for explicit approval before starting the next phase.
- Never fabricate results, timings, benchmarks, screenshots, test execution,
  or submission confirmation. Label planned, executed, passed, failed, skipped,
  and blocked work accurately.
- Run relevant real tests and fix failures before declaring implementation
  success. Preserve raw command output and exit status; investigate unexplained
  failures.
- Preserve original assignment documents byte-for-byte. Use synthetic fixtures,
  repository-relative paths, and isolated temporary directories.
- Never organize arbitrary user directories. Task 3 must default to preview and
  require explicit apply inside an approved workspace; reject unsafe roots and
  symlinks.
- The requested GitHub commit or PR is authorized for review; it does not
  authorize other publication or submission.
- Do not invent submission identity or assume track eligibility. Record missing
  authorization and access as blockers without blocking independent work.
- Use the existing checkout; do not create worktrees unless requested.
- Follow the active dual-track plans and status records in `planning/`.
